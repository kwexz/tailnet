# Модель безопасности, риски и ручные проверки

## Честная модель безопасности

Что действительно защищает это решение:

- Трафик между узлами шифруется WireGuard; ключи сессий согласуются через
  собственный control plane, а не облако Tailscale.
- Админка недоступна из интернета: nginx отдаёт чужим стандартный 404
  (`allow 100.64.0.0/10` + `deny all` + подмена 403), а из tailnet требует ещё и
  basic-auth, и API-ключ Headplane.
- DNS слушает только tailnet-интерфейс (UFW разрешает порт 53 только на
  `tailscale0`); control plane и DERP — единственные публичные поверхности
  плюс стандартные ssh/http(s).
- Pre-auth ключи по умолчанию живут 1 час; API-ключ — 90 дней с ручной ротацией.

Чего WireGuard **не** даёт (и это решение — тоже):

- WireGuard шифрует транспорт, но не защищает control plane, админку, DNS,
  бэкапы и процессы ротации. Компрометация VPS = компрометация всей сети:
  у атакующего окажутся база Headscale, ключи координации и вся топология.
- DERP-релей не расшифровывает полезную нагрузку, но видит метаданные
  (кто, с кем, когда, сколько). При exit node VPS-провайдер видит вообще весь
  интернет-трафик устройства в открытом для него виде на выходе.
- По умолчанию в сети действует политика `accept *` (любой узел → любой узел,
  любые порты). Это удобно, но означает свободное боковое перемещение после
  компрометации одного устройства. Сегментация — только ручной ACL в
  `policy.hujson`.
- DNS-запросы к внешнему миру идут на `1.1.1.1`/`1.0.0.1` открытым текстом
  (без DoH/DoT) — их видит путь от VPS наружу.
- Цепочка поставки (`curl | sh` установщика Tailscale, Docker-образы, Certbot)
  доверяется целиком; воспроизводимость сборки частичная (Headplane — `:latest`).

Кому доверяем: провайдеру VPS (железо, сеть, гипервизор), DNS-провайдеру
(Cloudflare для внешних имён), CA Let's Encrypt, апстримам Tailscale/Docker.
Если любой из них враждебен — модель не держится. Это нормально для self-hosted
сетапа, но должно быть сказано вслух.

## Аудит репозитория (статика, без запуска)

- Секретов, токенов и приватных ключей в репозитории **нет**. Все имена и адреса
  в скриптах и README — плейсхолдеры: `lan.example.com`, `example.com`,
  `100.64.0.0/10`, `100.64.0.4`, `172.30.0.0/24`, `203.0.113.0/24` (TEST-NET-3),
  `1.1.1.1`, `hskey-auth-...`, `<домен>`, `<ключ>`.
- `bash -n` чист для `setup-server.sh`, `setup-linux.sh`, `setup-mac.sh`, `tailnet-add`.
- Синтаксический разбор `setup-windows.ps1` через AST-парсер PowerShell — без ошибок
  (проверка выполняется скриптом `scripts/check-static.sh`, в CI — плюс ShellCheck
  и PSScriptAnalyzer).

## Реестр рисков

Серьёзность: В = высокая, С = средняя, Н = низкая, И = информация.

| ID | Риск | Серь. | Статус |
|---|---|---|---|
| R1 | `setup-server.sh` создаёт новый API-ключ Headscale при **каждом** запуске, старые не отзывает — ключи копятся, окно компрометации растёт | С | Документировано: чистить вручную (`headscale apikeys --help`: list/expire/delete), см. `docs/OPERATIONS.md` |
| R2 | Хеш basic-auth был MD5-crypt (`openssl passwd -apr1`) — устаревший, быстрый перебор при утечке файла | С | **Исправлено**: SHA-512 crypt (`-6`), `setup-server.sh` |
| R3 | `config.yaml`, `policy.hujson`, `headplane.yaml` (API-ключ, `cookie_secret`), `.setup-state` создавались с правами по умолчанию (читаемы всеми локальными пользователями) | С | **Исправлено**: `umask 077` на весь скрипт + явный `chmod 600` на секретосодержащие файлы |
| R4 | Строка бэкапа в cron дублировалась при каждом перезапуске (шаблон дедупликации не совпадал с реальной строкой) | Н | **Исправлено**: дедупликация по `backups/headscale-` |
| R5 | `tailnet-add` брал первую строку `headscale users list` как ID пользователя — а это заголовок таблицы, не ID | С | **Исправлено**: поиск имени из `.setup-state`, иначе первая числовая строка после заголовка |
| R6 | `tailnet-add` принимал любой срок ключа без проверки (`tailnet-add foo` молча падал внутри `headscale`) | Н | **Исправлено**: валидация `^[0-9]+[mhd]$` с понятной ошибкой |
| R7 | `setup-windows.ps1` писал `.setup-state.ps1` без экранирования кавычек в URL — ломалась загрузка состояния | Н | **Исправлено**: удвоение кавычек при записи |
| R8 | Перенастройка базовых параметров (FQDN/зона/IP) обновляет только `.setup-state`, а `config.yaml`, сайт nginx, dnsmasq, `base_url`/`public_url` остаются старыми — тихое расхождение | С | Документировано как ограничение идемпотентности, процедура синхронизации — в `docs/DEPLOYMENT.md` |
| R9 | Повторный запуск плодит дубликаты правил UFW (`allow` без проверки существования) | Н | Документировано: контроль через `ufw status numbered`, удаление дублей вручную |
| R10 | Нет валидации FQDN/email/диапазона IP (`ask_ip` ловит только формат, `999.1.1.1` пройдёт) — опечатка уедет в nginx/certbot/dnsmasq | Н | Документировано: сверять значения в диалоге и проверять `nginx -t`, `certbot`, `dnsmasq` после установки |
| R11 | Бэкап — tar живой sqlite-базы: восстановленная копия может быть непроверенной/битой | С | Документировано: восстановление только с остановленными контейнерами + проверка `tar tzf` + точка отката; для гарантии — бэкап при остановленном `headscale` |
| R12 | У бэкапов нет ротации, шифрования и выноса наружу — переполнение диска и потеря VPS = потеря сети | С | Документировано: пример `find -mtime +14 -delete`, `chmod 600`, вынос копии — в `docs/OPERATIONS.md` |
| R13 | Pre-auth ключи reusable: любой, кто перехватил ключ в окно действия, регистрирует своё устройство без approve | С | Документировано: окно 1 час по умолчанию, передача только по защищённым каналам, отзыв через `headscale preauthkeys --help` |
| R14 | ACL по умолчанию `accept *`: плоская сеть, боковое перемещение ничем не ограничено | С | Документировано как архитектурное решение; пример ужесточения — править `policy.hujson` вручную |
| R15 | `headplane:latest` не зафиксирован — повторное развёртывание не воспроизводимо, апстрим может подсунуть любое изменение | С | Документировано: зафиксировать тег/digest в `docker-compose.yml` вручную |
| R16 | `curl | sh` установщиков (Tailscale, Docker) и пакеты без проверки подписей сверх TLS | С | Документировано как принятое доверие апстриму; проверять контрольные суммы/подписи вручную при паранойе |
| R17 | Внешний DNS — plaintext к Cloudflare; путь от VPS видит запросы | Н | Документировано; кому критично — выносить DoH/DoT резолвер самостоятельно |
| R18 | Control plane знает топологию и участвует в согласовании ключей; DERP видит метаданные ретранслируемого трафика | С | Документировано как часть модели угроз (см. выше) |
| R19 | Basic-auth админки можно отключить в диалоге — тогда остаются только tailnet-ACL и API-ключ | Н | Документировано; рекомендация — не отключать |
| R20 | `setup-windows.ps1` подключается без ключа (нужен approve в админке), а команды `tailnet-add` — с ключом (без approve). Такое несоответствие легко вводит в заблуждение | И | Документировано в `docs/DEPLOYMENT.md` |
| R21 | `--accept-dns` различается по платформам (Windows/macOS — true, Linux — false) | И | Документировано; это осознанный выбор, не баг |
| R22 | Заглушка 404 для чужих содержит маркер `nginx` — минимальный фингерпринт | И | Принято; кому критично — обезличить тело ответа |
| R23 | Нет rate-limit на `/` и `/admin`, нет security-заголовков — перебор и fingerprinting не затруднены | Н | Зафиксировано как точка hardening (fail2ban/rate limit — вручную) |
| R24 | Android/iOS-клиенты в README упоминались рядом с проверенными — фактически не проверены | И | **Исправлено в документации**: помечены как непроверенные, без инструкций «как проверенных» |

## Что исправлено кодом (сводка)

1. `setup-server.sh`: `umask 077` + `chmod 600` для `config.yaml`, `policy.hujson`,
   `headplane.yaml`, `.setup-state`; хеш basic-auth `-apr1` → `-6`;
   исправлена дедупликация cron-строки бэкапа; `${HOSTNAME_FQDN#*.}` вместо
   `echo | sed` (эквивалентно, чище для ShellCheck).
2. `tailnet-add`: удалён мёртвый код (`HS= docker`); выбор пользователя — по имени
   из `.setup-state` с fallback на первую числовую строку; валидация срока ключа.
3. `setup-mac.sh`: разбор хоста из URL средствами parameter expansion вместо
   `echo | sed` (эквивалентно).
4. `setup-windows.ps1`: экранирование кавычек в `Save-State`.

Поведение инфраструктуры (маршруты, firewall-семантика, DNS-семантика, порты,
политики) этими правками **не менялось** — только права, хэши, дедупликация и
валидация ввода.

## Ручные проверки — только в изолированной среде

Запрещено: запускать установочные скрипты на рабочей машине, трогать действующие
firewall/DNS/маршруты/Docker/VPN, подключаться к боевому VPS. Всё ниже —
на чистом тестовом стенде (VM/VPS, снапшот до старта).

### Сервер

1. Чистая Ubuntu + A-запись на тестовый домен → `sudo bash setup-server.sh`,
   сверить каждый ответ диалога.
2. `docker ps`: контейнеры `headscale`, `headplane` в статусе Up.
3. `curl -sf https://<тест-домен>/key -o /dev/null && echo OK` — control plane доступен.
4. Из интернета (не из tailnet): `curl -s -o /dev/null -w '%{http_code}' https://<тест-домен>/admin`
   → ожидание `404`, а не `401`/`403` (маскировка).
5. Из tailnet: `curl -u <логин>:<пароль> https://<тест-домен>/admin` → ожидание `200`/редирект в админку.
6. `ufw status verbose`: 22/80/443/tcp, 3478/udp открыты; 53 — только `in on tailscale0`.
7. `ss -ulnp | grep :53`: dnsmasq слушает только на tailnet-IP.
8. `ls -l /opt/headscale/config /opt/headscale/.setup-state /etc/nginx/.htpasswd_headplane`:
   секретосодержащие файлы — `600` (htpasswd — `640 root:www-data`).
9. Повторный `sudo bash setup-server.sh` без смены параметров: данных не теряет,
   `crontab -l` — по одной строке certbot и бэкапа, `ufw status numbered` — без
   лавины дублей, `docker exec headscale headscale apikeys list` — зафиксировать рост
   (R1) и отозвать лишнее.
10. Бэкап: дождаться `04:30` или выполнить строку cron вручную при остановленном
    `headscale`; восстановление — строго по процедуре из `docs/OPERATIONS.md`
    (stop → `tar tzf` → точка отката → распаковка → up → `nodes list`).
11. Ротация API-ключа по процедуре из `docs/OPERATIONS.md`: админка работает,
    старый ключ отозван.

### Клиенты (Windows / macOS / Linux)

12. Подключение ключом из `tailnet-add`: узел появляется в Machines без approve.
13. Подключение через `setup-windows.ps1` без ключа: узел требует approve — подтвердить
    в админке, проверить вход в сеть.
14. `tailscale status` показывает `direct` между двумя тестовыми узлами
    (или зафиксировать `relay` и причину — NAT стенда).
15. `nslookup <тест-домен> <tailnet-IP-VPS>` резолвится; при включённом стороннем VPN —
    проверить сценарий split-tunneling/`hosts` из `docs/DEPLOYMENT.md`.
16. Exit node: включить на Windows и macOS (меню + CLI), проверить смену egress-IP;
    выключить — возврат прямого маршрута.
17. `tailnet-add foo` завершается понятной ошибкой валидации, ключ не создаётся.

### Не проверяется в этом проекте

18. Android/iOS: поголовно непроверенные пути. Любая инструкция по ним до проверки
    на стенде считается черновиком, а не документацией.
